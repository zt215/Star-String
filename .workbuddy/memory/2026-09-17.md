# 2026-09-17

## 手势动作菜单改为按模型能力动态生成（用户反馈「选完功能模型根本没用」）

用户原话：手势操控动作不是固定的选项，检测模型支持的功能，表情动作等等，
然后在手势菜单显现，现在选择完功能模型根本没用。

### 根因（三条，全是实测确认的）

1. `gesture.py` 的 `ACTION_LABELS` 是写死的 7 项，和模型实际能力毫无关系。
2. Live2D 侧根本对不上：`set_expression("smile")` 要求模型里有名叫 `smile` 的
   表情，而实际模型的表情名是 `生气`/`爱心`/`脸红`（云吞kumo）、`兽耳隐藏`/
   `发卡1`（玳瑁猫）、`Fcl_ALL_Joy`（VRM 0.x）。永远匹配不上 → 静默降级 →
   `_pick_motion_group(("Tap","Flick","Idle"))` 也常匹配不上 → 什么都不发生。
3. VRM 侧的 `play_motion` 只 `set_drive(arm_swing_r=110, elbow_r=70)` 一次，
   下一帧动捕的 `set_drive_params` 全量覆盖，一帧都看不到。

另外探测发现：**VTS 系模型（云吞kumo/玳瑁猫/nekoN）的 model3.json 完全没登记
Expressions 和 Motions**，`.exp3.json` / `.motion3.json` 就散在模型目录里。
live2d-py v3 提供 `LoadExtraExpression` / `LoadExtraMotion` 可以补注册。

### 改了什么

- 新增 `app/services/model_actions.py`：纯函数能力探测 + 菜单生成 + 动作 id
  解析（`none` / `motion:<真名>` / `expression:<真名>`，兼容旧 id）。
- `live2d_view`：新增 `_register_extra_assets()`（加载后补注册，`LoadExtraMotion`
  返回值 >0 才算成功，并清 `_motions_cache`）、`_runtime_*` 查询、
  `available_actions()`；`expression_names()`/`motion_groups()` 改为
  「运行时 ∪ 注册成功的补注册项」。
- `vrm_view`：`play_motion` 重写为定时器驱动的骨骼动画（wave/nod/shake/bow/clap，
  首尾包络归零），`set_drive_params` 走 `_merged_drive()` 让动画层压过动捕；
  `set_expression` 先精确匹配真实表情名再回退语义预设；新增 `available_actions()`。
- `home_window`：新增 `_available_actions` / `_capabilities_from_menu` /
  `_rebuild_gesture_menus` / `_gesture_menu_hint`，在模型加载与类型切换时重建
  下拉框并迁移失效映射；`_trigger_gesture_action` 改为前缀解析。
- `model_view_base`：接口补 `available_actions` / `set_expression` / `clear_expression`。
- `gesture.py`：`ACTION_LABELS` 降级为旧 id 的中文名，注释说明不再是菜单数据源。
- 新增 `tools/gesture_actions_selftest.py`（133 条断言，10 组）。

### 过程中踩到并修掉的坑

- `default_action_for` 的「复用兜底」在强匹配阶段也跑了，导致第二个手势把第一个
  刚占下的名字抢回去（点赞和 OK 双双指向「爱心」）。
- 同一个兜底写成 `_pick(strong or generic, pool)`，`strong` 非空就把通用偏好顶掉，
  于是 peace 这类没有强暗示的手势白白退化成「不响应」。
- `_rebuild_gesture_menus` 会改写 `gesture_actions`。构造界面时还没加载模型，
  一刷就把用户已存的映射全洗成「不响应」——加了 `caps.is_empty()` 保护。
- 老配置存的是 `wave`，下拉框数据是 `motion:wave`，不规范化 `findData` 就失配，
  界面显示回「不响应」（看着像没生效）。现在解析得出来也要转成前缀形式。

### 回归

6 个自检全绿：gesture / gesture_actions / hand_drive / lipsync / vrm_arm / ui_smoke。

## 修正静态手势判据：握拳误判点赞 + 手指正对摄像头识别不到指向

用户原话：点赞与握拳的识别有偏差，大部分握拳都是点赞，然后指向方向，摄像头在
侧面识别到手指就可以指向，但是当手指正对摄像头的时候，就是识别的握拳和点赞，
识别不到正对的指向。

### 根因（两条，都已在自检里形式化复现）

1. **握拳→点赞**：旧 `states["thumb"]` 取 `max(IP 指节夹角分, reach 分)`。
   握拳时拇指往往**是直的**（只是横搭在四指上），IP 夹角接近 180° → 那一项直接
   满分 → `thumb_out=True`。再叠上 `count==0` 与「拇指尖高于手腕」→ 判成点赞。
   实测合成用例：旧代码 拇指分=1.000（IP=180.0°, reach=1.81）→ `thumb_up`。
2. **正对镜头认不出指向**：判据只吃 21 点二维像素坐标，而单目 2D 在手指正对
   镜头时会把伸出的食指压成一小段、另外三根卷起的手指又正好朝镜头方向折、
   投影下来反而显得笔直。实例（0.0/75°倾角，正交投影）：指向 2D→`None`、
   85°→`open_palm`、90°→`None`，全都不是 `point`。

### 改了什么

- `gesture.py`：`classify(points, world=None)` / `finger_states(points, world=None)`
  新增可选的**世界坐标**（米制三维）参数，几何量（指节夹角、尺度归一化、捏合
  距离）优先用它算；`_point`/`_distance`/`_angle_deg` 改成维度无关（二维点自动
  补 z=0）。二维像素点仍保留，用于「拇指尖是否高于手腕」这种画面方向判断。
- 拇指「张开」换成**离食指近端指骨有多远**：`min(点-线段距离(拇指尖, 5→6),
  点-线段距离(拇指尖, 9→10)) / (腕→中指 MCP)`，再与 IP 伸直度取 min。阈值
  `_THUMB_TUCK=0.34` / `_THUMB_SPREAD=0.64`。握拳 ≈0.2、点赞 ≈0.8，余量充足。
- `classify` 的提前返回改为**只在没有世界坐标时**才因画面里手没宽度而放弃
  （90° 完全正对时 `image_scale` 会退化成 0，但有世界坐标照样解得出）。
- `motion_capture.py`：新增 `_hand_world`，在 `_detect_hands` 里读
  `result.hand_world_landmarks`（缺该项时该手填 `None`，保持与 `_hand_points` /
  `_hand_labels` 的索引对齐）；`_update_gestures` 把世界坐标一并传给 `classify`。
  三处 `_hand_points` 归零的地方同步归零 `_hand_world`。
- `tools/gesture_selftest.py`：加 `_hand3`（罗德里格斯公式搭的三维手模型）、
  `_view`（绕画面横轴倾斜后正交投影成二维像素点）、`check_world_plumbing`
  （假 landmarker 结果喂 `_detect_hands`，验证字段名与整条接线）。
  用例：握拳·拇指伸直搭食指（旧代码判点赞）、点赞·拇指略弯（防止收紧过头）、
  指向/握拳/张开/比耶 × 掌心朝镜头 / 75° / 85° / 90°。

### 回归

6 个自检全绿；`gesture_selftest` 19 项（含「正对镜头时只喂二维点必然解不出」
的反向断言，防止哪天视角不再退化、用例失去防护作用）。

## 修正手臂摆角：手在下方，模型却举手

用户原话：胳膊的位置有问题啊，我胳膊在下方，它就是举手的高度了（截图里模型是
**右臂**抬到脸侧、左臂正常）。

### 定位过程

先确认叠加层语义：橙色骨架线是 YOLO 身体关键点（BGR `(0,165,255)`），粉色是手部
21 点，所以摆角确实由「肩→腕」解出。然后用 `MotionCapture.__new__` + `_solve_arm`
做数值扫描（肩固定在画面 y=0.5，腕位遍历），一次就打出问题：

```
胸前偏外 同肩高  腕=(0.68,0.55) 手在肩下 |Δy|=5  -> swing=137.6 肘弯=126   ← 手在肩下却举手
胸前偏外 略低    腕=(0.70,0.62) 手在肩下 |Δy|=12 -> swing=114.7 肘弯=111
```

### 根因（两个，都在同一条链路上）

1. **肘位两解的挑选顺序错了。** 两杆 IK 的两个解是「肘在肩腕连线两侧」的镜像。
   旧实现按「谁更靠外」挑，而手臂弯得厉害时（手抬到胸前/肩高附近，两解分得很开），
   更靠外的那支恰好是把肘甩到肩**上方**的——上臂于是朝上指。左右臂的"外侧"方向相反，
   所以看起来像"只有一侧出错"。
2. **`swing` 没折回有符号区间。** `atan2` 给的是 `[0°,360°)`，「自然下垂、肘略偏
   内侧」落在 340° 附近，而 `_write_arm` 的钳位是 `[-40,165]` → 直接夹成 165°（举手），
   且 `_unwrap` 会一直贴着 165° 绕 → **手臂永久卡在举手姿态**。

### 改了什么

- `motion_capture._solve_arm`：肘位挑选改为 ①手不在肩上方时取**肘在肩下方**的解
  （人不可能把手放在胸腹前还把肘抬过肩）；②同侧时再比外侧；③打平才取更靠下。
- `_solve_arm` 返回前把 `swing` 折回 `(-180, 180]`（`if swing > 180: swing -= 360`），
  位置在 `_unwrap` **之前**。
- `tools/vrm_arm_selftest.py` 新增断言：手略低于肩时**左右两侧**摆角都 < 50°
  （旧实现约 124°）、左右镜像解出同一摆角、手在肩前下方时 swing ∈ [-40,50) 且
  肘弯 > 100°（旧实现 ≈113°，缺折回会被钳成 165°）。

### 回归

6 个自检全绿（vrm_arm 154 项）。修复后同一扫描：手在肩下的各个位置 swing 落在
-33° ~ +63° 自然区间，340° → -20.3°。

## 修正「只露手 / 只露一侧肩」时手臂朝天飞

用户原话：摄像头内就露手，识别到手腕，肩膀位置也能看见，推算不出来手臂在哪吗，
露手就肩膀往天上飘，手肘在哪呢就肩关节朝天飞。

### 定位过程

先用 `MotionCapture.__new__` 把「有肩/无肩 × 手在画面各处」整表打出来，一次就
看出退化路径的输出**与手的位置完全无关**：

```
只露一侧肩（另一侧 conf=0.1） -> pose 作废 -> swing=83.60°
YOLO 检不到人，手在画面下缘   -> swing=83.60°
YOLO 检不到人，手在画面左上   -> swing=83.60°
```

### 根因（四个）

1. **`_pose_from_body` 要求两侧肩都可信**，只露一侧肩就把整份 pose 作废。
2. **退化路径读 `drive["arm_l"]`**，而那个量在**手被检测到时恰恰不被填充**——
   `_extract_drive` 只在 `not self._hand_detected` 时才调 `_apply_arms`，于是它恒
   为初值 0.0，映射出 `swing = (0 + 0.76) × 110 = 83.6°`。**手一进画面，两条手臂
   同时抬成举手**，且与手在画面哪个角落无关。
3. **躯干长度只由髋位决定**，而只露上半身时 YOLO 仍会外推一个乱飞的髋坐标，
   实测同一姿态下 torso 在 0.06~0.97 之间跳（真值 ≈0.49），摆角因此差 25°。
4. **`_solve_arm` 的单位方向用了裁剪后的距离**：腕点落在肩上时 `reach ≈ 0`，除以被
   撑到 `d_min` 的 `d` 得到零向量，肘位坍缩到肩上 → 摆角/肘弯被误判成 0。

### 改了什么

- `_pose_from_body` 改为 classmethod：**只要至少一侧肩**就算数，返回 `sides`；
  躯干长度分层估计并返回 `torso_src`（`hip` → `shoulder`(肩宽×1.18) → `default`），
  髋不可信时不再采用髋坐标。
- `_apply_arms_ik`：按 `sides` 只解看得见的手臂，另一侧走兜底；`torso_src=="default"`
  时用手部掌骨换真尺子；`half`/`d_min` 移进循环按侧计算。
- 新增 `_hold_arm`（抽出的保持逻辑）、`_screen_left_dx`（无肩点时的画面手性）、
  `_frame_aspect`、`_screen_wrist`（退化路径的腕点输入）、`_hand_palm_scale`
  （腕→中指掌骨，`arm_len = 6.0 × palm`）、`_arm_from_screen`（画面中心当肩 +
  假设臂长，仍走 `_solve_arm`）。
- `_arms_from_screen` 重写：不再读 `arm_l`，改用当帧腕点走两杆 IK，并接入保持窗口。
- `_solve_arm`：单位方向改用**未裁剪**的 reach 归一化。
- `_smooth_value` / `_hold_arm` 加实例字段兜底，`__new__` 构造的实例不再崩。
- `tools/vrm_arm_selftest.py` 新增 `test_partial_body()`（15 条）：髋不可信时 torso
  与髋坐标无关、只露一侧肩能解出该侧手臂（旧 83.6° → 今 20.9°）、掌骨尺子把摆角
  从 52.6° 拉回 20.9°、只露手时手越抬高摆角越大且单调、手丢失保持后松开、
  腕点落在肩上时肘弯仍 >100°。

### 回归

6 个自检全绿：gesture 19 / gesture_actions 133 / hand_drive 24 / lipsync 22 /
vrm_arm 175（新增 15）/ ui_smoke OK。

### 顺带发现（未改，待查）

`arm_swing_*`/`elbow_*`/`arm_fwd_*` **只有 VRM 消费**；`live2d_view` 一个都不读，
它只用 `arm_l`/`arm_l_x`。而 `arm_l`/`arm_r` 在手在画面里时不被更新（恒 0），
Live2D 的手臂在手出现时会僵在静息位；那个量的量纲 `(肩y - 腕y)/肩宽` 还会饱和到
±1 之外（手垂在身侧实测 -1.775）。需要单独一轮排查。

## 动作僵硬 / 非人类姿势：肘位挑选从「硬切」改成「连续插值」

用户原话：仿真模型，不能做出非人类的操作，然后动捕检测找到手的位置，胳膊的位置，
记住人的空间位置，映射到模型上，这样才能实现人在做什么动作，模型做什么动作，
现在模型做的动作太僵硬了。

### 定位过程（先用探针把「僵硬」量化，再动手）

临时写了几个探针（用完即删），用 `MotionCapture.__new__` 逐帧喂腕点，统计
`max_step`（单帧最大角度变化）、`flips`（方向反转次数）、`mean_step`：

- 手腕绕肩平滑画圆：`max_step=23.2, flips=1`
- 手从肩下笔直抬到肩上：手在肩**正下方**穿过时 `34.8`，偏外一点穿过时 `29.6`
- 手在肩附近 ±8px 微动：`max_step=2.99`，轨迹在 6~12° 之间来回弹（僵硬的来源）
- 逐帧扫 `_solve_arm` 的原始输出，把断裂点直接打出来：

```
腕 x=300（肩内侧 100px）: dy=-12px -> swing= 141.5
                          dy= -9px -> swing= -39.9   <-- 一帧跳 181°
腕 x=100（肩外侧 100px）: 第13帧 85.3 -> 42.4        <-- 一帧跳 43°
```

### 根因（三个，本质是同一个：肘位挑选全是硬判据）

1. **肘位两解用硬切**：`if wy >= sy and above1 != above2` / `elif out2 > out1`。
   两条先验（「肘在肩下」/「更靠外」）互相切换的那一点，恰好是**两支解的高度之一
   与肩同高**的时候；切换点附近两支解能差上百度的上臂朝向，于是手在肩线旁边轻轻
   一动，上臂就整条翻过去。
2. **`+= 360` 绕回在「手臂水平」处是断的**：`if swing < 0 and up_comp > 0: swing += 360`
   以 `up_comp` 的符号为界，而折在胸前时肘指向**内侧水平**，`up_comp` 正好在 0 附近
   翻号 → 同一个方向一会儿是 `-52°`、一会儿是 `+267°`，再叠上折叠兜底的混合，
   输出差 181°。`up_comp > 0` 这条判据本意是「手举过头顶解出 -174° 要绕回 +186°」。
3. **「手举过肩」这条前提用了双侧判据**：手越过身体中线伸到对侧肩前时高度正好与
   肩齐平甚至高几个像素，`wy >= sy` 判成「不在肩下」→ 先验 A 失效 → 先验 B 挑出
   「肘抬到肩以上」的解，上臂朝上指。

### 改了什么（全在 `motion_capture`）

- `_solve_arm` 的肘位挑选**不再有硬切**：两条先验各自的解都用 `tanh((a-b)/band)`
  软化后加权，再按「两支解分居肩上下 × 手没举过肩」的连续权重插值
  （`_ELBOW_BLEND_BAND = 0.5`，单位 = 上臂长）。姿态分得越开越接近硬选，
  正好在临界点上平滑过渡。
- 「手没举过肩」改成**单侧**斜坡：`raised = clamp(-dy / (0.6 × 臂长), 0, 1)`。
- 新增「手臂折得紧时把肘高抹平到与肩同高」：`reach < 0.6×half` 时按 `|dy|` 过渡到
  `sy`（两支镜像解的中点，上臂水平朝外），解决手贴肩线上下晃动时的 65°↔99° 弹跳。
- 删除 `_unwrap`（唯一调用点已移除）——它拿「上一帧**已钳位**的平滑值」当参考，
  一旦被钳过一次参考值就偏 180° 以上，之后每个角度都被绕到错误的一支。
- 折叠兜底的「内侧」判据**改按半肩宽衡量**（原来除以 `0.35×臂长`）：手到躯干中线
  本来就该算「折在身前」，原来只算 0.8，剩下 20% 仍带着两支解各自的方向。
- 折叠兜底**去掉「离肩近就拉回」**，只认「确实折进身体轮廓内侧」：手抬到肩上方
  一点点、肘朝侧面抬平同样离肩很近，但那条手臂是抬着的，硬拉回会在手划过肩水平线
  时挖出一个 V 形坑（实测 65°→8°→115°）。
- `_solve_arm` 加 `elbow_hint`（YOLO 7/8 号肘点，`_ELBOW_HINT_CONF=0.50`，
  到肩距离要在 `0.5~1.6×上臂长` 内）优先消歧镜像解；有可信肘点时不走插值那条路。

## 第八轮：单指被认成握拳 + 单指与握拳互相触发

用户原话：识别不对，我的手势是单手指，录制时显示的是握拳。我执行单指和握拳，识别
提示都是握拳，没有出现过我的手势1的显示，两个动作都会执行自定义的动作。

### 定位（先写探针量化，不猜）

临时探针 `tools/_probe_gesture_split.py` 用项目自带的合成手型走**真实链路**量了三件事，
一次就看清了（用完已删）：

1. `classify` 在合成数据上**是对的**（单指→point，含三维手模型倾斜投影）；
2. 但**姿势特征里「单指 vs 握拳」的距离只有 0.153**，比默认容差 0.16 还小 ——
   「两个动作都触发同一个自定义手势」当场解释清楚了；
3. 逐指驱动值的距离表还暴露了更狠的一条：**手指正对镜头（tilt 75°~85°）时，
   二维投影把握拳的手指压平**，逐指弯曲度只剩 `[0.24, 0.00, 0.24, 0.45]`
   （中间那根直接读成「伸直」），而「单指」是 `[0.00, 0.00, 0.24, 0.45]`
   —— 两者几乎一样。

### 根因（三条，都是可复现的度量缺陷，不是调参）

1. **加权 RMS 会摊薄稀疏特征**。手型是「一根手指定形状」，逐指权重 0.5、总量 24 维，
   单根手指全反过来只把距离抬到 0.153。同理「单指 vs 比耶」也是 0.153。
2. **分类器的绝对阈值有死区**。指节状态 0.35~0.6 既不算伸直（>0.6）也不算弯曲
   （<0.35），四指全落进去就 `count==0 → 握拳`；真实的手做单指时食指常只伸到 130°
   上下，正好落这儿。
3. **驱动链路只吃像素坐标**。`_hands_to_drive` 里 `_finger_curl` 用像素点，手正对
   镜头时投影把卷起的「指尖-指根距离 / 三指节总长」从 1.00 压到 0.6 以下，弯曲度
   直接失真（既坏姿势特征，也让模型手指乱动）。

### 改了什么

- `pose_gesture.distance()`：取「加权 RMS」与「**单根手指最大差异 × 0.6**」
  （`_peak_finger_delta` × `_PEAK_FINGER_WEIGHT`）的较大值。系数 0.6 是两个数字量出来的：
  单指↔握拳 → 0.60（> 容差上限 0.35，任何档位都拦得住）；同一姿势重摆、手指各偏 0.25
  → 0.15（≤ 标准档 0.16，不会灵敏到触发不了）。换算：**标准档容忍的单指误差 ≈ 0.27**。
- `gesture.classify`：`count==0` 前加相对判据 —— 「最直的一根领先第二名多少」
  （`_SOLO_GAP=0.30`、`_SOLO_MIN=0.35`）。握拳四指齐平（领先 0.05）→ 仍握拳；
  半伸的食指（状态 0.500）→ 指向；食指状态 0.167 时必须仍判握拳（反向守住）。
- `motion_capture._hands_to_drive`：手指弯曲度改用**世界坐标**（缺了才退回像素）。
  三个量三个理由、别一刀切：手腕位置用归一化、弯曲度用世界、**手腕 roll 留像素**
  （那是屏幕空间的量）。
- `motion_capture`：新增 `_hand_shapes`（**每帧**覆盖）与 `current_hand_shapes()`；
  `_hands_summary` 只报这一帧，判不出手势写「已检测（手型未识别）」。**不能**用
  `_gesture_active` 显示 —— 那是去抖后的触发状态，判不出时保留旧值，会让用户看到
  「一直做单指、界面一直显示握拳」。
- `home_window`：新增 `_hand_shape_text()`，录制弹窗多显示「手型：左手 指向
  （食/中/无名/小/拇 0.00 1.00 …）」—— 是没读到手指还是判据认错，一眼能看出。

## 第九轮三补：音量监控加高把上面的内容压没了

用户原话：在屏幕上哪有这么长，音量监控上方的设置页面根本被挤压的看不见文字。

根因：我上一轮把音量监控面板从 196/146 加高到 290/220，而变声页左右两栏是普通
QVBoxLayout——窗口高度不够时它会把每项压到 sizeHint 以下，上面的变声参数 /
口型卡就被挤没了。**加高一块 = 挤压全部**，这类页面必须让内容可滚动。

### 改了什么（`home_window.py`）

- 新增 `_make_scroll_column(panel)`：把面板内容包进 `QScrollArea`（widgetResizable），
  返回内容用的 QVBoxLayout——**调用处的后续代码一行不用改**。变声页左右两栏都换用它。
- 音量监控高度回调：228/176（compact 118→84 柱），面板 290→228、220→176。
- ⚠️ **QScrollArea 的 viewport 默认白底**，直接把深色主题盖成白色。必须：
  `scroll.setStyleSheet("QScrollArea, QScrollArea > QWidget > QWidget { background: transparent; }")`
  （`> QWidget > QWidget` 选中的是 widgetResizable 塞进来的内容宿主）。
- ⚠️ 编辑教训：给 `_build_rvc_page` 里的左/右栏做替换时，我按 strip 过的打印输出写了
  **4 空格缩进的 old_string**，替换后把 8 空格的方法体改出了 IndentationError（两处）。
  `python -c` 打印源码时**永远带行号和原始缩进**（或直接用 Read），别用 strip 过的行拼 old_string。
